# 02 — A tokenizer is the model's vocabulary contract

**Outcome:** Encode and decode text exactly, and distinguish two different kinds of training. **Time:** 25 minutes. **Prerequisite:** lesson 01.

## Understand

In this course, tokenizer training counts frequent adjacent pieces and learns merge rules. Model training uses gradients to update neural-network weights. Learning a useful way to split text does not teach a new model grammar or facts.

You can reuse an existing tokenizer with a randomly initialized model. The model is still being trained from scratch. Conversely, replacing a trained model's tokenizer is not a harmless settings change: the learned input and output weights depend on the meanings of the IDs.

Our first tokenizer uses UTF-8 bytes. IDs 0–255 are byte values; ID 256 is reserved for end-of-document (EOS). Some characters need multiple bytes, so one character is not always one token. Spaces, tabs, and line breaks are data too.

```text
python labs/lab.py tokenize --text "Hello, café 🌍"
```

**Expected:** the decoded text equals the input, including accent, space, and emoji. You may see several IDs for one visible character. The default command with no `--text` also tests an actual newline.

## Work one merge

Given the byte sequence for `abab`, the pair `a,b` occurs twice. Adding a merged token for `ab` turns four IDs into two. The next merge is learned from the sequence after the previous merge. At use time the saved merge rules are applied in their learned order. Our optional BPE lab always retains the initial 256 byte values, including bytes absent from its training documents.

This is a deliberately small implementation of byte-level BPE. Production tokenizers also make choices about pre-tokenization, normalization, special tokens, and efficiency. The course tokenizer merges within entire documents, and never across documents during tokenizer training. [Hugging Face's BPE explanation](https://huggingface.co/learn/llm-course/chapter6/5) develops the algorithm further.

## Predict, then check

1. If two tokenizers both have 320 entries, can they necessarily share a model's weights?
2. What should happen to an unseen emoji?
3. Does `decode(encode(text)) == text` prove the model understands the text?

**Answers:** (1) No; the ID-to-piece mapping can differ. (2) Our byte tokenizer represents its UTF-8 bytes, so encoding and decoding remain exact. (3) No; it verifies representation, not learning.

**Common snag:** Randomly generated bytes may be invalid UTF-8. Generation displays a replacement character for invalid sequences; encoding and decoding real input text uses strict checks. Those are distinct cases.
