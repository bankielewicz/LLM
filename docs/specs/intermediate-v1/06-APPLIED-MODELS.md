# Applied models, adaptation, inference, and electives

Status: normative implementation specification. Edition: 2026-09-28. This section specifies the pretrained-model path, adapter training, chat generation, model comparison, lexical retrieval, and the safe-model-modification elective. It does not change the preserved foundation course or its Python lab.

The pretrained path uses one pinned public model and the dependency versions in [00-DECISIONS.md](00-DECISIONS.md). The browser-only edition may display recorded artifacts but cannot execute any operation in this section. All executable behavior is provided by the loopback companion and uses registered identifiers rather than learner-supplied filesystem paths or URLs.

## APP-001 — Operation and model identity boundaries

The implementation MUST preserve these distinct operations and descriptions:

| Operation | Input model state | Changes learned weights | Required output identity |
|---|---|---:|---|
| `model_prepare` | no local pretrained model | no | verified base-model registry ID |
| `adapter_train` | verified frozen base model | adapter weights only | adapter run and checkpoint IDs |
| `adapter_resume` | adapter checkpoint including optimizer and RNG state | adapter weights only | child checkpoint with parent ID |
| `evaluate` | base model or adapter checkpoint | no | immutable evaluation artifact ID |
| `context_preview` | tiny, base, or adapter tokenizer identity | no | request-bound token/context preview ID |
| `chat_generate` | base model or adapter checkpoint | no | immutable generation artifact ID |
| `generate` | tiny-v2 checkpoint | no | plain prompt-continuation artifact ID |
| `retrieval_build` | text corpus | no | immutable lexical-index ID |
| `retrieval_query` | lexical index and query | no | ranked-hit artifact ID |

`adapter_train` and `adapter_resume` MUST keep every base-model parameter frozen. `context_preview`, `chat_generate`, `generate`, `evaluate`, `retrieval_build`, and `retrieval_query` MUST execute with gradients disabled and MUST NOT update a model, optimizer, tokenizer, dataset, conversation, or index. `model_prepare` MUST only acquire and verify the eight allowlisted files in APP-002. Training a tokenizer, training tiny-v2 from random weights, resuming tiny-v2, adapting the pretrained base, previewing context, and generating output MUST remain separate controls, API operations, result types, and learner-facing labels.

Every applied artifact, through its own fields or its immutable registered run/checkpoint/model identity references, MUST carry `model_profile_id`, repository, revision, download-manifest SHA-256, tokenizer SHA-256, chat-template SHA-256, dtype, device, dependency-lock digest, and the companion source revision. An adapter artifact through the same closed identity references additionally MUST carry adapter configuration, base-model registry ID, dataset artifact ID and SHA-256, parent checkpoint ID or null, seed, completed optimizer update, and training preset ID. A label entered by a learner MUST NOT substitute for any identity field.

The tiny-v2 backend MUST identify its artifacts with `model_family: "tiny-v2"` and `interaction_mode: "continuation"`. The pretrained and adapter backends MUST identify their artifacts with `model_family: "smollm2-135m-instruct"` and `interaction_mode: "chat"`. The runtime MUST reject a tiny checkpoint passed to `chat_generate` and a pretrained or adapter ID passed to `generate` with reason `SUBJECT_INCOMPATIBLE` before a compute job starts.

## APP-004 — Chat serialization and supervised-loss mask

The authoritative template is the exact `chat_template` string in the pinned `tokenizer_config.json`; its UTF-8 SHA-256 is `872be49dbb638044ad01b60388f48d469ff2980e5f0dccdc22ec907db54d0788`. It emits `<|im_start|>{role}\n{content}<|im_end|>\n` for each message, inserts the model's default system message when the first message is not `system`, and emits `<|im_start|>assistant\n` when `add_generation_prompt` is true. Runtime rendering MUST call `apply_chat_template(..., tokenize=True)` so special tokens are not added twice.

Training examples in `applied-intents-v1` contain one user message plus an expected response. The collator MUST render an explicit message sequence of the task system message, the fixture user message, and an assistant message whose content is the fixture's exact `expected.response`, with `add_generation_prompt=False`. The task system message is exactly `You sort customer support requests. Reply with exactly two lines. Line 1: INTENT= followed by one of account_access, billing_refund, order_status, password_reset, product_information, technical_issue. Line 2: REPLY= followed by one short helpful sentence.` It is used by both adapter presets, by evaluation profile `applied-intents-greedy-v1` and by every capstone evaluation, so the baseline and the adapter receive the same instruction; free chat (APP-009, APP-010) keeps the template's default system message. It MUST separately render the system and user messages with `add_generation_prompt=True`. The resulting prompt token IDs MUST be an exact prefix of the full token IDs; otherwise the record MUST fail preprocessing with `ASSISTANT_BOUNDARY_MISMATCH`.

Labels for every prompt-prefix token MUST be `-100`. In the full IDs, the prompt prefix is followed by assistant content, one `<|im_end|>` token ID 2, and the template's trailing newline token sequence. Labels from the first assistant-content token through that first terminating ID 2 MUST equal input IDs; every token after it, including the trailing newline, MUST be `-100`. Missing ID 2 or additional non-newline serialized content after it fails `ASSISTANT_BOUNDARY_MISMATCH`. Padding labels MUST be `-100`. The implementation MUST NOT request `return_assistant_tokens_mask`, because the pinned template contains no `{% generation %}` block and therefore does not promise such a mask. Each full training sequence MUST be at most 512 tokens; an overlength authored fixture MUST fail dataset validation rather than truncate a response. Padding MUST be on the right to the longest sequence in the batch, although the v1 training batch size is one.

The preprocessor MUST retain, per record, the input-token count, prompt-token count, supervised-token count, and SHA-256 of the integer token-ID sequence. A record with zero supervised tokens MUST fail with `EMPTY_SUPERVISED_TARGET`. The course MUST display the serialized text and a prompt-versus-assistant mask view for at least one fixture before the learner can start adapter training.

## APP-005 — Applied task and deterministic evaluation

The v1 SFT dataset `applied-intents-v1` MUST contain 84 authored synthetic records across six slices: `account_access`, `billing_refund`, `order_status`, `password_reset`, `product_information`, and `technical_issue`. It has 60 training, 12 validation, and 12 test records; every slice contributes 10/2/2 respectively. `scenario_group_id` values MUST be disjoint across splits. Adapter training MUST read only `train`. Automatic checkpoint evaluation and selection MUST read only `validation`. The test split MUST be read only by an explicit `evaluate` job. `applied-intents-v1` and `capstone-support-v1` are authored in scenario groups: each group is one distinct support situation with one reply, told in paraphrased user requests ([fixture-source.json](fixtures/data/fixture-source.json) `instruction_sets.slices[].applied_groups` and `capstone_groups`). applied-intents-v1 has seven groups of two per slice; capstone-support-v1 has four groups of three, two, one and two per slice. Every group lies in exactly one split. Paraphrases in one group differ in at least three words. Within each fixture, no two user messages in different splits have word-set Jaccard similarity above 0.5, computed after NFKC, casefolding, replacing punctuation and symbols with spaces, and deleting every token that contains a digit, so no held-out item rewords or re-codes a training item. `check_fixture_oracles.py` enforces these properties, and `generate_fixtures.py` checks that the DAT-003 audit detects a seeded exact copy, a seeded near copy and a seeded split group.

Evaluation profile `applied-intents-greedy-v1` MUST order records by Unicode code-point order of `record_id`; serialize the user message using APP-004; decode greedily with temperature 0, top-p 1, at most 64 new tokens, and stop at EOS or the maximum. It MUST retain every raw generated token ID and decoded string.

For a record, the intent parser splits lines exactly as Python `str.splitlines()` (LF, CR, CRLF, VT, FF, FS, GS, RS, NEL, U+2028, U+2029), trims each line exactly as Python `str.strip()` with no arguments, skips empty trimmed lines, and takes the first remaining line. Intent values are case-sensitive. metric-oracle-v1.json freezes separator, padding, 240/241-scalar and case examples and per-slice aggregates. `exact_intent_match` is 1 only when that line is exactly `INTENT=<expected.intent>`. `response_schema_valid` is 1 only when there are exactly two nonempty trimmed lines, line one is `INTENT=<one of the six allowed slice values>`, line two begins `REPLY=`, the suffix contains 1 through 240 Unicode scalar values, and no other nonempty line exists. The response text is not automatically graded for helpfulness or factual correctness.

The evaluation artifact MUST report integer numerator, integer denominator, and JSON-number ratio for `exact_intent_match` and `response_schema_valid_rate`, overall and for every slice. Ratio is the IEEE-754 binary64 quotient encoded as the shortest round-trip JSON number; display rounding does not alter stored values. It MUST include the ordered record IDs, expected intent, parsed intent or null, per-record `response_schema_valid`, raw text, token IDs, stop reason, model/checkpoint identity, and decoding parameters. [fixtures/applied/metric-oracle-v1.json](fixtures/applied/metric-oracle-v1.json) freezes parser examples and expected aggregates. There is no passing score, required improvement, or claim that this synthetic task measures general instruction following.

Teacher-forced validation mean negative log likelihood MUST also be calculated across only supervised response tokens: sum of per-token cross-entropy divided by the count of non-`-100` labels. It is a checkpoint tie-breaker, not a quality threshold. Perplexity is `exp(mean_nll)` only when the exponent is finite; otherwise the stored value is null.

Capstone preset `smollm2-capstone-lora-v1` MUST use the same model, LoRA target/configuration, dtype, context, batch size, optimizer, learning-rate, clipping, and no-packing values. ## APP-007 — Deterministic training, validation, and selection

Before model or optimizer construction, the worker MUST seed Python and Torch with the preset seed and enable deterministic algorithms. CUDA runs MUST set deterministic backend flags and MUST fail with `DETERMINISTIC_KERNEL_UNAVAILABLE` rather than silently choose a nondeterministic kernel. The dataset order for pass `p`, starting at zero, MUST be the result of a Torch CPU generator seeded with `seed + p`, applied as one `randperm(training_record_count)`. Training MUST continue across pass boundaries until the requested update count is reached. Resume MUST restore the current permutation and next-record cursor rather than reshuffle the incomplete pass.

One optimizer update MUST accumulate the preset's consecutive one-record forward/backward passes: four for intents and three for capstone. Each microbatch loss MUST be the mean over its supervised labels divided by that accumulation count before backward. Before the first microbatch of every accumulation group, the worker MUST snapshot the current pass number, permutation, next-record cursor, Python RNG state, Torch CPU RNG state, and applicable CUDA RNG state. After the final microbatch, the worker MUST calculate the L2 norm over trainable gradients, fail on a nonfinite norm, clip to 1.0, perform one AdamW step, zero gradients with `set_to_none=True`, and increment `completed_update`. Cancellation is checked after each microbatch and before each optimizer step. If cancellation arrives during an accumulation group, the worker MUST discard the incomplete gradients, restore that group's boundary snapshot, leave adapter tensors, optimizer state, `completed_update`, and incumbent selection at their last completed-update values, then atomically write the resumable cancellation checkpoint. Resume therefore replays the whole interrupted group; it never skips partly consumed records or performs an extra update.

Validation MUST run at update 0 and the preset cadence: every 10 intents updates or every 5 capstone updates, including a terminal requested update not on cadence. It reads the complete validation split in record-ID order and produces APP-005 generation metrics plus teacher-forced mean NLL. For both presets, the selected checkpoint is the candidate with, in order: greatest exact-intent numerator; greatest schema-valid numerator; lowest finite mean NLL; earliest update. Null or nonfinite NLL ranks below every finite NLL. The comparator MUST store each compared value and the selected rule. Test data MUST NOT participate in this selection.

The metrics stream MUST contain one row per completed optimizer update with update, the preset accumulation count of ordered record IDs, mean supervised-token loss across those microbatches, unclipped gradient norm, clipped gradient norm, learning rate, elapsed seconds, cumulative examples, the worker's peak resident memory in bytes so far, and peak reserved CUDA memory in bytes so far (`torch.cuda.max_memory_reserved()`; null on CPU profiles). Peak resident memory is the worker process's peak resident set size: `ru_maxrss` from `resource.getrusage` in KiB times 1,024 in WSL, and the peak working-set size from `GetProcessMemoryInfo` on native Windows. Validation rows MUST contain the complete metric numerators/denominators and selection result. A nonfinite loss or gradient MUST fail with `NONFINITE_TRAINING_VALUE`, retain the last safe checkpoint, and record the update and value category. There is no automatic retry or learning-rate change.

## APP-008 — Safe checkpoints and exact resume

A checkpoint MUST be written to a new temporary directory and atomically renamed after all files and their SHA-256 manifest are durable. It MUST include `adapter_model.safetensors`, `adapter_config.json`, `optimizer.safetensors`, `rng.safetensors`, `trainer_state.json`, `metrics.jsonl`, and `manifest.json`. `adapter_model.safetensors` contains only PEFT adapter tensors. Its tensors are exactly, for each layer i from 0 to 29, `base_model.model.model.layers.{i}.self_attn.q_proj.lora_A.weight` [8, 576], `base_model.model.model.layers.{i}.self_attn.q_proj.lora_B.weight` [576, 8], `base_model.model.model.layers.{i}.self_attn.v_proj.lora_A.weight` [8, 576] and `base_model.model.model.layers.{i}.self_attn.v_proj.lora_B.weight` [192, 8], all float32: 120 tensors and 460,800 scalars. The companion writes them under these names whatever adapter name the PEFT library uses internally. Any other name, shape or dtype, a missing tensor or an extra tensor fails load with CHECKPOINT_INCOMPATIBLE. `optimizer.safetensors` contains AdamW tensor state keyed by stable adapter parameter name. `trainer_state.json` contains scalar optimizer state, completed update, accumulated examples, pass number, permutation, next-record cursor, best-candidate tuple, and dependency/profile identities. `rng.safetensors` contains Torch CPU and, when applicable, CUDA RNG byte tensors. Python RNG state MUST be encoded as a bounded JSON array of integers, not pickle.

No checkpoint file may use pickle serialization. Loading MUST first validate the manifest, every listed digest, model profile, base revision and manifest digest, chat-template digest, adapter preset, dataset ID and digest, dependency-lock digest, device profile, and completed-update consistency. A mismatch MUST fail with `CHECKPOINT_INCOMPATIBLE` and MUST NOT load any tensor into a model or optimizer.

`adapter_resume` MUST create a new run and preserve the parent checkpoint. It accepts only `checkpoint_id` and `additional_updates`; model, dataset, preset, seed, optimizer settings, and device profile are inherited and immutable. It MUST restore adapter, optimizer, RNG, permutation, cursor, step, and best-candidate state before reading the next training record. An equivalence acceptance test MUST compare an uninterrupted 60-update CPU run with a 40-update run resumed for 20. Adapter/optimizer tensors, ordered record IDs, numerical loss/gradient/learning-rate fields for updates 41–60, selected checkpoint update, and generated validation token IDs MUST be exactly equal. Elapsed seconds, timestamps, job/run/checkpoint IDs, parent IDs, and artifact digests that contain those identities are expected to differ and are excluded. CUDA resume comparison uses the same numerical/state assertions within one qualified host/profile; cross-device equality is not claimed.

## APP-009 — Decoding, output events, and cancellation

Every `generate` and `chat_generate` request MUST reference a successful `context_preview` artifact. `context_preview` is a tokenizer-only job: it MUST NOT load model weights, run inference, or update state beyond its immutable preview artifact. Its request uses `backend: "tiny"` with the prospective `model_id`, prompt, and decoding fields, or `backend: "chat"` with the prospective subject, messages, decoding fields, and optional paired `conversation_id`/`expected_conversation_revision`. It MUST contain none of `preview_artifact_id` or `context_preview_digest`. The worker resolves the subject, tokenizer, chat-template, device, runtime profile, and context limit from the registry before tokenization.

For `backend: "tiny"`, the canonical generation request is the validated preview value after replacing `operation: "context_preview"` plus `backend: "tiny"` with `operation: "generate"`. For `backend: "chat"`, it is the validated preview value after replacing `operation: "context_preview"` plus `backend: "chat"` with `operation: "chat_generate"`. No other field is added, removed, or rewritten. The worker serializes that object with Python 3.12 `json.dumps(value, sort_keys=True, separators=(",", ":"), ensure_ascii=False, allow_nan=False)`, UTF-8 encodes it with no trailing LF and no Unicode normalization, and stores its SHA-256 as `canonical_generation_request_sha256`.

The preview artifact MUST store exactly the OpenAPI preview fields: `backend`; `subject_identity_sha256`; `tokenizer_sha256`; `template_sha256` as the chat-template digest or null; resolved `device`; `original_input_token_count`; final `input_token_ids` and `input_token_count`; `serialized_text`; `dropped_message_indices`; `cropped_input_tokens`; `effective_context_budget`; and `canonical_generation_request_sha256`. `context_preview_digest` is SHA-256 over the same Python-canonical bytes of that field object, excluding `preview_artifact_id`, `context_preview_digest`, `operation`, and `artifact_ids`. The response adds the registered `preview_artifact_id`, `context_preview_digest`, `operation`, and `artifact_ids` after digest calculation.

Before job creation, the service MUST validate the request schema, preview ID/digest, referenced IDs, and recomputed `canonical_generation_request_sha256`. It MUST NOT import the tokenizer or reproduce serialization, tokens, or truncation. The accepted job's worker MUST resolve current identities and profile, re-tokenize and reserialize, reproduce the preview field object, and compare its digest before loading weights. A service-level request/artifact mismatch is rejected with `CONTEXT_PREVIEW_STALE`; a worker identity, profile, context, tokenization, serialization, truncation, field, or digest mismatch fails the job with that code before inference. Evaluation needs no preview. E02 MUST create a new preview after retrieval.

`chat_generate` accepts subject `{model_id}` for the prepared base or `{model_id, adapter_checkpoint_id}` for an adapter; messages; `max_new_tokens` 1 through 128; temperature from 0 through 2 inclusive; top-p from 0.05 through 1 inclusive; and integer seed 0 through 4,294,967,295. It MUST use a custom one-token decode loop, not pass an assumed `generator` keyword to `model.generate`. Temperature 0 performs argmax with the lowest token ID winning an exact-logit tie. For positive temperature, the loop divides logits by temperature, softmaxes in float32, sorts by descending probability then ascending token ID, removes every token whose preceding cumulative probability is at least top-p while always retaining the first token, renormalizes, and calls `torch.multinomial(probabilities, 1, generator=job_generator)`. `job_generator` is `torch.Generator(device=selected_device).manual_seed(seed)`. No top-k, beam, or repetition penalty is applied. Invalid combinations fail before queuing with `INVALID_SAMPLING_PARAMETERS`; temperature 0 requires top-p 1.

Generation MUST stop after EOS token 2, after `max_new_tokens`, or when cancellation is observed before the next decode step. Stop reasons are exactly `eos`, `length`, or `cancelled`. PAD is EOS for this model and therefore also stops generation. The final text is decoded from new token IDs only, with `skip_special_tokens=true` and `clean_up_tokenization_spaces=false`. The stored artifact MUST include request messages, full serialized input, input token IDs and count, dropped message indices, effective context limit, sampling values, seed, subject identity, new token IDs, generated-token count, final text, stop reason, start/end time, and job ID.

The event stream MUST emit `phase_changed` with exactly `{phase:"generating"}`. Coalesced progress has exactly `{current,total,unit,message}`: generated count, `max_new_tokens`, `tokens`, and `Generating`. Terminal has only `{state,reason_code,checkpoint_id,checkpoint_step}`; both checkpoint fields are null. It carries no output. After completed terminal, the client MUST fetch `GET /jobs/{id}` for the typed result and artifact references. Cancellation retains a partial artifact with `stop_reason: "cancelled"`, ends `interrupted` with no typed result, and never reports `completed`.

`generate` for tiny-v2 remains plain prompt continuation. Its UI MUST display `Prompt & continue`, checkpoint ID, tokenizer digest, step, context cropping, temperature, and seed. It MUST NOT accept role messages, use the pretrained chat template, or be described as an assistant. The preserved lab's current one-shot continuation behavior is evidenced at [course/labs/lab.py](../../../course/labs/lab.py) lines 59–76 and its non-chat teaching architecture at [course/labs/model.py](../../../course/labs/model.py) lines 1–5.

## APP-010 — Conversation validation and context truncation

A chat request MUST contain 1 through 64 messages. Roles are `system`, `user`, and `assistant`; content is a nonempty valid UTF-8 string of at most 8,192 bytes with no NUL, and combined message content is at most 32,768 UTF-8 bytes. At most one system message is allowed and it MUST be first. Remaining roles MUST alternate user/assistant, start with user, and end with user. Consecutive equal roles, an assistant-first transcript, or an assistant-final transcript fail with `INVALID_CONVERSATION`.

The input budget is `512 - max_new_tokens`. The runtime first serializes the complete transcript with `add_generation_prompt=true`. If it exceeds the budget, it removes the oldest complete user-plus-assistant pair after the system message, reserializes, and repeats. It MUST never remove an explicit system message or the final user message. Indices removed refer to the zero-based positions in the original request and MUST be recorded in order. If no removable complete pair remains and the serialized input still exceeds the budget, the request fails before generation with `CONTEXT_TOO_LONG`; it MUST NOT crop token arrays or message text.

## APP-013 — E02 lexical retrieval with evidence

E02 MUST use no embedding model and trigger no download. `retrieval_build` takes a registered corpus split, `text_field: "text"`, and `max_features` from 100 through 20,000. Records each have a unique `record_id` and nonempty `text`. It normalizes text with Unicode NFKC, applies Unicode case folding, extracts ASCII terms matching `[a-z0-9]+`, and rejects a document with no terms. It rejects a document with no retained term after max_features truncation by failing the retrieval_build job with RETRIEVAL_DOCUMENT_NO_RETAINED_TERMS. The query vector is the normalized tf*idf of the query's in-vocabulary terms. Dot products and norms sum with math.fsum over terms in Unicode code-point order. The stored index is INT-008 canonical JSON (terms and record IDs in code-point order, floats in shortest round-trip form) and its SHA-256 is over those bytes. Scores are unclamped binary64 values and may exceed 1 by rounding; the response schema has no upper bound. If vocabulary exceeds `max_features`, it retains terms by descending document frequency and then ascending term. For document `d` and retained term `t`, `tf(t,d)=count(t,d)/total_extracted_terms(d)`, `df(t)` is the number of documents containing `t`, and `idf(t)=ln((1+N)/(1+df(t)))+1`. The stored vector is `tf*idf`, L2-normalized. Terms, record IDs, and sparse indices MUST be stored in Unicode code-point order with corpus ID, corpus SHA-256, algorithm ID `tfidf-nfkc-casefold-v1`, and index SHA-256.

`retrieval_query` applies the same normalization/tokenization, uses corpus IDF, discards out-of-vocabulary terms, L2-normalizes a nonzero query vector, and calculates cosine similarity by sparse dot product. Results sort by descending unrounded float64 score and then ascending `record_id`; `top_k` is 1 through 20 and returns `min(top_k,N)` hits, including zero-score ties. A query with no vocabulary term fails with `RETRIEVAL_QUERY_NO_TERMS`. [fixtures/applied/retrieval-corpus-v1.json](fixtures/applied/retrieval-corpus-v1.json) and [fixtures/applied/retrieval-query-oracle-v1.json](fixtures/applied/retrieval-query-oracle-v1.json) copy the canonical authored eight documents and six queries and freeze each expected top-three `record_id` and float64 score. Acceptance requires exact rank/ID equality and absolute score error no greater than `1e-15`; stored scores remain the implementation's unrounded binary64 values.

The E02 results screen MUST show an `Answer with retrieved evidence` action; using it is voluntary and is not required for E02 completion. The action MUST use an already prepared base or adapter and cannot prepare another model; when none is prepared it is disabled with the text `Prepare the pinned base first`. It constructs one explicit system message: `Answer only from the supplied evidence. Cite each factual sentence with [RECORD_ID]. If the evidence is insufficient, say "Insufficient evidence."` Its user message is `Question:\n{query}\n\nEvidence:\n`, followed for each ranked hit by `[{record_id}]\n{text}\n` in rank order. That transcript then uses `chat_generate` and APP-009/010. `retrieval-manual-v1` is an eight-document mechanics fixture: its scores demonstrate the algorithm and do not measure retrieval quality. The generation artifact MUST embed the retrieval artifact ID and ranked record IDs/ranks/scores in its `retrieval` member and the SHA-256 of the exact augmented prompt, whose text is the artifact's serialized input.

Automated citation checks MUST only verify that each bracketed identifier names one of the supplied hits and that at least one supplied identifier appears unless the exact output is `Insufficient evidence.` They MUST NOT claim that a sentence is supported. The learner's evidence record MUST identify a quoted answer claim, its cited source text, and a self/human judgment of supported, unsupported, or ambiguous. Retrieval completion is an elective badge and cannot replace a required module or capstone artifact.
