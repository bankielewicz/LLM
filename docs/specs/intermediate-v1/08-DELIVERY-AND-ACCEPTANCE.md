# Delivery and acceptance specification

Status: NORMATIVE TARGET. This file specifies implementation order and release gates. The authoring task executes document checks only. Product execution, installation, native browser behavior, model training, and educational effectiveness are NOT_RUN.

## DEL-001 — Deliver dependency-ordered vertical slices
The implementation MUST use the following sequence. Each slice must have its own runnable outcome, source diff, updated trace, and case results. Later slices do not excuse an earlier failing case.
| Slice | Required deliverable | Gate before next dependent slice |
|---|---|---|
| S0 Contracts and custody | Protected-file hash gate; validated schemas/OpenAPI/fixtures; edition compiler; test scaffolding; exact direct dependencies and per-profile locks | Every schema/fixture/reference check passes; original course and legacy importer regressions retained |
| S1 Local companion | Authenticated loopback service, storage root, session flow, dataset registry, one-worker jobs, errors/events/cancellation/recovery | Unauthorized requests cannot queue jobs; crash/recovery, disk-full and queue boundaries pass |
| S2 Existing-model integration | Tiny-v2 wrapper, source-equivalence tests, standalone tokenizer, train/evaluate/resume/generate, checkpoint registry | Legacy parity controls and distinct operation effects pass; real tiny job and safe checkpoint resume demonstrated |
| S3 Learning and evidence | Modules P00,13-15, new navigation, dataset clinic, diagnosis, evaluation, notebook/progress migration, artifact verification | A learner can finish one local data-to-training-to-evaluation path; static mode remains useful; no progress-to-competence promotion |
| S4 Applied models | Pinned explicit model preparation, baseline inference, LoRA train/resume, context-aware chat, fair comparison | Base frozen/adapters changed checks; correct masking/template; model identity and export/import round trip pass |
| S5 Completion | Modules16-20,E01,E02; independent capstone; bundle reuse; accessibility and native supported-profile qualification | Entire frozen acceptance denominator satisfied against one candidate; missing native tests block release |
A slice can be developed in parallel only if its input contracts are already frozen. Changes to a frozen contract require consumer updates and affected case reruns in the same candidate. Stubs may support development tests but cannot satisfy an end-to-end or native qualification case.

## DEL-002 — Produce installable profile artifacts
The delivery MUST include source, a Python wheel for the companion, static frontend assets, applied curriculum sources and generated content, deterministic fixture definitions/files, setup instructions, uninstall/data-retention instructions, direct dependency declarations, and three complete transitive hash lockfiles for the named execution profiles.
The direct versions in D10 are fixed. Each lockfile MUST bind package version, wheel filename, source index and SHA-256 for every runtime dependency. CPU Torch must resolve through its CPU index, not a default CUDA wheel; the CUDA profile uses the explicitly selected cu126 build. Only the selected profile is installed into its own virtual environment. The setup documentation must not advise global installation, administrator privileges, disabling browser protections, or silently substituting packages.
The builder MUST run the actual environment's package consistency check and a startup/import preflight, retain raw output, and record the complete installed package list. Public package metadata alone is not compatibility evidence. A pin that cannot pass qualification requires a spec amendment with the old failure retained; the builder may not silently relax it.
An offline installation package is not required. After explicit model preparation and dependency installation, required lessons and local execution MUST run without external network access. The documentation must distinguish setup downloads from later offline operation.
Official wheel-source reference: https://pytorch.org/get-started/previous-versions/ (2.8.0 CPU/cu126 options checked 2026-09-28). [Direct package metadata](evidence/dependency-public-metadata.json) is discovery evidence only.

## DEL-003 — Freeze candidate and acceptance denominator
Before product qualification begins, the validator MUST create a candidate receipt containing: Git commit; Git tree; protected-file hashes; specification revision and aggregate digest; all contract and fixture hashes; dependency-lock hashes; built wheel/static archive hashes; model repository revision and file hashes; profile hardware/software identities; and the exact acceptance registry hash.
The canonical case definitions are generated from `trace/*.json` into `acceptance-cases.json`; `requirements.json` is their requirement index. A case execution unit is `case_id × profile`. The validator MUST expand every listed profile before execution and freeze the total. There is no percentage threshold, sample-based waiver, or removal of blocked cases. Each case is conjunctive: every listed action, boundary and expected observation must pass. Where a case says every/each, the validator expands the finite rows from its cited table/schema into named subchecks and freezes their list before execution; a partial subcheck run cannot produce PASS.
Native browser cases MUST additionally retain a result row for Edge and Firefox under the applicable static/Windows/WSL profile; the case cannot pass until every required engine passes. Device/source-oriented cases do not require a browser merely because the profile names a desktop OS.
Case definitions may be corrected during development, but qualification must retain the previous registry, state why the oracle changed, and start a new identified candidate/qualification attempt. Any changed implementation source, built artifact, dependency lock, model file, contract, fixture, or acceptance registry creates a new candidate_id. Every mandatory case/profile/browser execution row for that candidate begins NOT_RUN and MUST execute against that candidate. Earlier passes remain historical evidence only; they cannot be carried forward to qualify changed bytes.

## DEL-004 — Keep verification stages separate
Required stage order:
1. **Document/contract checks:** JSON parsing, schema validation, OpenAPI reference resolution, requirement-to-case coverage, fixture oracles, protected-source custody.
2. **Unit and boundary tests:** pure tokenization, masks/shapes, validation/import, split/audit, progress merge, state machines, decoding, checkpoint metadata, and malicious representation variants.
3. **Service integration:** real loopback authentication, filesystem confinement, jobs/events/recovery, operation adapters, cancellation, replay/idempotency, bundle import/export and storage transactions.
4. **Native model execution:** selected CPU/CUDA profiles, pinned model, actual train/resume/evaluate/inference controls; no simulated runner may satisfy this stage.
5. **Native browser/accessibility journeys:** complete processes, native file selection, persistence/reload, two browser engines, keyboard, assistive technology, zoom/reflow, reduced motion, forced colors, connection loss/recovery.
6. **Learner task assessment:** objective evidence plus named self/human scoring of the defined reasoning rubric. This qualifies the individual submission only; it does not prove educational efficacy.
All failed, interrupted, blocked, and skipped observations MUST be retained. Diagnostic retries receive incrementing attempt IDs; the newest passing attempt cannot erase earlier failures.

## DEL-005 — Define executable acceptance evidence
A result row MUST include `case_id`, `profile`, `browser` when applicable, `candidate_id`, `attempt`, `started_at`, `ended_at`, `status`, `command_or_journey`, `actual_observation`, `expected_reference`, `artifact_paths`, `artifact_sha256`, and `reviewer`. Allowed status values are `NOT_RUN`, `PASS`, `FAIL`, `BLOCKED`; reason is mandatory for FAIL/BLOCKED. Skips are recorded as BLOCKED with a reason, never omitted.
Evidence goes to `qualification/<candidate_id>/<profile>/<case_id>/attempt-<NNN>/`. Paths are candidate-owned and relative to the qualification root. Every expected output is written freshly; a stale artifact cannot satisfy a case. A manifest records paths, sizes and hashes. No credentials, bearer/CSRF tokens, bootstrap secrets, or private learner corpus content belong in a public test report.
Where a case expects rejection, record the HTTP status/error code, unchanged job/registry counts, and unchanged protected data. Where a case expects real execution, record process ownership, job transitions, measured values, checkpoint identity, and declared operation effects. Exit zero alone is insufficient.
Native UI evidence consists of a written action/observation trace plus relevant screenshots or accessibility-tree excerpts. Screenshots alone cannot establish keyboard focus, file-picker behavior, localStorage persistence, screen-reader announcements, or reduced-motion behavior.

## DEL-006 — Run the mandatory integrated learner journeys
In addition to section cases, the release MUST execute these complete flows, maintaining one learner state throughout each flow:
- **J1 Foundation continuity:** fresh static origin -> Start -> foundation lesson -> worked answer -> explicit read/practice/self-check states -> local save -> reload -> Continue -> export -> separate-origin import. No intermediate artifact verification is granted by these actions.
- **J2 Real tiny experiment:** local launch -> pair -> preflight -> audited dataset -> predict -> review configuration -> tiny_train -> real metrics -> checkpoint -> evaluate -> fixed-prompt generation -> linked notebook/evidence. Output provenance names the actual job and checkpoint.
- **J3 Interruption/recovery:** long bounded local job -> cancel -> retained terminal record and safe-checkpoint status -> new resume child where a checkpoint exists -> service restart -> session re-pair -> recovered job/evidence. No duplicate job or invented completion.
- **J4 Applied adaptation:** explicit pinned model preparation -> baseline task evaluation -> adapter_train -> adapter checkpoint -> repeat held-out evaluation -> chat with selected identity -> comparison and limitations. A negative quality result may be valid evidence; frozen base and protocol consistency are mandatory.
- **J5 Portable reuse:** export a complete selected bundle -> validate in an empty storage root -> import with mapped local IDs -> load/evaluate/generate using the imported checkpoint -> compare permitted deterministic outputs -> verify imported provenance and original lineage.
- **J6 Bad-input recovery:** invalid scalar/markup legacy result -> malformed progress -> corrupted/path-traversing bundle -> rejected dataset -> unavailable model -> storage write failure -> recover without losing prior valid notes/runs. The user can identify what failed and export surviving state.
- **J7 Access:** repeat J2's principal actions by keyboard and J4's input/output reading with NVDA, Edge and Firefox; verify focus/announcements,360px layout,200% text,400% zoom/reflow, reduced motion, forced colors and chart-table equivalence.
No journey may depend on an undisclosed hosted service or API fallback. Recorded fixtures remain labelled and cannot replace J2-J5's actual execution.

## DEL-007 — Bound security and persistence release gates
Qualification MUST demonstrate that cross-origin websites, missing/expired tokens, wrong Host headers, replayed bootstrap tokens, oversized uploads, JSON scalar substitutions, crafted archive paths, symlink/junction escapes, unsupported pickle/model artifacts, and malformed event cursors do not execute jobs or overwrite valid state.
Process cancellation and service shutdown MUST affect only owned workers. Interrupted writes must not make incomplete files appear committed. A crash between file write and registry commit must recover or quarantine deterministically. Import validation happens before registry mutation; checksum consistency does not create trusted execution provenance.
The app must handle full disk, revoked write access, missing data/model files, incompatible checkpoint identity, and restart recovery with the exact result/error semantics in the runtime/data contracts. Authentication boundary tests use inert payloads and isolated fixture roots; they must not access unrelated user files or change host-wide protections.

## DEL-008 — Complete accessible behavior, not CSS presence
The release MUST meet the concrete accessibility cases in the UX contract and the applicable WCAG2.2 A/AA success criteria across all shipped screens and complete processes. The validator must inventory the applicable criteria and record PASS, FAIL, or NOT_APPLICABLE with a source-backed reason. A component-library claim or static contrast audit cannot substitute for behavior checks.
The native accessibility matrix includes Windows NVDA with Edge and Firefox, keyboard-only use, native file pickers, browser back/forward/reload, forced-colors mode, prefers-reduced-motion, focus visibility/obscuration, form errors, live announcements, non-color status meaning, chart tables, and touch target size. Test unbroken long error strings, Unicode text, and large imported-note content.
If administrator policy prevents a browser, screen reader, or other relevant tool, record BLOCKED and the affected cases. Do not change policy or use an alternate rendering path to claim the unavailable behavior passed.

## DEL-009 — Publish only the qualified audience and artifacts
This specification task MUST NOT publish or deploy. During later implementation, static Site updates preserve the existing audience unless the user changes it; a local companion is distributed as an installable artifact rather than deployed as a public training service.
Before a release is described as complete, its published static archive and companion distribution MUST be bound to the qualified source commit and specification revision. Native publication success establishes delivery, not product acceptance. Release notes state supported profiles, installed model revision, known constraints, full qualification summary, and any unqualified audience/platform.
Rollback uses a previously retained complete distribution and independent learner-data backup. Runtime storage migrations MUST retain their before-image according to the data contract; destructive downgrade is forbidden. If safe downgrade is unsupported, the installer must refuse it and describe recovery rather than rewrite data.

## DEL-010 — State exact completion and remaining work
Implementation is complete only when all requirements are delivered, all required case/profile/browser executions pass, protected source is unchanged, and a reviewer confirms cross-contract consistency. All authoring, implementation, integration, browser, publication and learner-assessment statuses must be reported separately.
This package's own final review MUST report which document checks were actually run, which author drafts were challenged, what changed after review, and any unresolved contradictions. A document-review pass must not use a product-readiness badge.
There is no scheduled continuation, live monitoring, external model installation, publishing action, or background learner training implied by this specification. Those require a later implementation instruction.
