# Learner experience specification — Intermediate buildout v1

Status: NORMATIVE TARGET. Product behavior described here is not implemented or tested by this specification task. This document is subordinate to [00-DECISIONS.md](00-DECISIONS.md).

The existing interface establishes the calm workshop, single continuation action, short-session lesson rhythm, distinct progress marks, simulations, recorded-run reading, notebook, and evidence checklist that this release extends. The current route switch and screens are in [dist/app.js](../../../dist/app.js#L10-L45); current visual tokens and breakpoints are in [dist/styles.css](../../../dist/styles.css#L1-L8). The source interaction contract requires exact content rendering, honest recorded-data labels, independent progress storage, and distinguishable simulation, record, connection, checkpoint, and storage states ([course/design/INTERACTION_CONTRACT.md](../../../course/design/INTERACTION_CONTRACT.md#L5-L38)).

Existing <code>#/lesson/:moduleId</code> links MUST use <code>history.replaceState</code> once to become <code>#/learn/:moduleId</code>, without adding a history entry, losing query state, or changing progress.

Legacy hashes from the preserved app redirect once with <code>history.replaceState</code>: <code>#/roadmap</code> to <code>#/learn</code>, <code>#/results</code> and <code>#/checkpoints</code> to <code>#/runs</code>, <code>#/labs</code> to <code>#/lab</code>, <code>#/capstone</code> to <code>#/learn/12</code>; <code>#/explore/:tool</code>, <code>#/glossary</code> and <code>#/reference/:path</code> remain canonical. In static mode <code>#/runs</code> hosts the preserved recorded-run import (<code>Import recorded run</code>) and lists imported records labelled <code>Recorded result · imported snapshot</code>. An unknown hash renders <code>That page isn't in this course.</code> with a link to Home and focus on main.

The persistent primary navigation MUST contain Home, Learn, Lab, Runs, Playground, Notebook, and Evidence in that order. Settings MUST be reachable from the application header. The current page MUST use <code>aria-current="page"</code>; a module link MUST announce its module ID, title, required/elective kind, and progress state. Every nested page MUST provide one contextual back link that returns to its parent without discarding form state. Browser Back and Forward MUST restore the route, scroll position, selected tab, and unsent form fields held in session memory.

The global header MUST contain the current section name, runtime status button, storage status text, Search, and Settings. Runtime status labels are exactly <code>Static course</code>, <code>Checking local runtime</code>, <code>Pair this tab</code>, <code>Local runtime connected</code>, <code>Connected · storage read-only</code>, <code>Incompatible local runtime</code>, <code>Session expired · pair again</code>, or <code>Connection lost</code>. No green dot or icon may be the only status indication.

Search accepts 1–100 Unicode scalar values, applies Unicode NFKC, casefolding, Unicode-whitespace collapse and trim, then literal substring matching; it performs no stemming or synonym expansion. Searchable fields are module title, outcome, authored heading, glossary term, and glossary definition. Rank is exact title/term, title/term prefix, title/outcome/heading/term substring, then definition substring; ties use curriculum order, source heading order, then glossary term code-point order. Return at most 50 results. Submitting an empty normalized query focuses <code>Search results</code> and displays <code>Enter a word or phrase to search the course.</code>; no matches focuses the same heading and displays <code>No course matches for “QUERY”.</code>. Result links identify field and module, focus the destination heading, and MUST NOT mutate progress. The 1–100 bound counts Unicode scalar values of the raw query before normalization; a longer query shows the inline error <code>Search is limited to 100 characters.</code> on the field, keeps focus in the field and runs no search. Query and indexed text pass through the same pipeline: NFKC, Unicode 15.1 full case folding (CaseFolding.txt statuses C and F, shipped as a generated table because browsers have no case-fold primitive), NFKC again, then every maximal run of White_Space characters becomes one U+0020 and the result is trimmed. The index is built from compiled course content: titles, outcomes and sequence numbers come from `course/curriculum.json` for modules 00–12 and from the `title`, `outcome` and `sequence` members of `fixtures/curriculum/curriculum-overlay.json` for P00, 13–20, E01 and E02. A result is one (module, field, heading occurrence) or one (glossary term, field) pair, so a module matching in its title and in two headings yields three results. Results sort by the tuple (tier 1–4 in the order listed above; module results before glossary results; module sequence ascending; field order title, outcome, heading; heading source index ascending; glossary term code-point order). The first 50 are shown, with <code>Showing 50 of N results</code> when N exceeds 50. Submitting sets the hash to <code>#/search?q=</code> followed by the raw query as UTF-8 percent-encoded except RFC 3986 unreserved characters, pushing one history entry; loading that hash runs the same search and Back restores the previous query and results.

## UX-002 — Home, learning path, and continuation

Home MUST present exactly one visually primary action. For a new learner (no module has any learning flag set) it is <code>Start learning</code> and targets module 00 unless the learner explicitly chooses P00. For a returning learner it is <code>Continue learning</code>. Progress dimensions are independent booleans/timestamps, never an ordered enum. Its deterministic target order is: the most recently updated required module with <code>reading=true</code> and <code>read=false</code>; the most recently updated required module with <code>read=true</code> and either <code>practiced=false</code> or <code>self_checked=false</code>; the lowest-sequence unresolved required evidence item that is eligible; the lowest-sequence required module with at least one true and at least one false learning flag; then the lowest-sequence required module whose four flags are false. Timestamp ties use curriculum sequence ascending. The Continue rules walk a traversal set: foundations 00–12 followed by applied 13–20, in sequence 0–20 (the `sequence` of `course/curriculum.json` and of the overlay). In these Continue rules only, 'required module' means a member of that set; completion counts keep the overlay's `completion_required` (13–20). P00 (sequence -1), E01 (21) and E02 (22) are never Continue targets. The required evidence items are exactly FOUNDATION-12 (module 12) and CUR-005 through CUR-012 (modules 13–20), each with its module's sequence. An item is resolved when any local evidence record with that requirement_id has verification_status artifact_verified. An unresolved item is eligible when its module's four learning flags are all true and every blocking prerequisite of that module (CUR-002) is resolved; its target is <code>#/evidence</code> with focus on that requirement's form. When all four learning flags are true for all required modules, Continue targets <code>#/evidence</code>: the next unresolved required criterion when one exists, otherwise the evidence summary with primary action <code>Review evidence and export</code>. A failed or interrupted job MUST appear immediately below the primary action as <code>Review interrupted job</code> or <code>Review failed job</code>; it MUST NOT replace course continuation or imply failure completion.

Home MUST show separate counts for Read, Practiced, Self-checked, Artifact verified, and Independently reviewed. It MUST NOT collapse these into a completion percentage. The learning path MUST show P00 outside the required sequence, foundations 00–12 as preserved content, required applied modules 13–20, and electives E01/E02 in distinct labelled groups. Locked prerequisites MUST explain the exact prerequisite and provide a link to it; navigation remains available for review, and only the dependent graded practice submission is disabled.

The foundation bodies MUST remain unchanged. Supplement cards are an edition overlay with <code>card_id</code>, <code>source_lesson_id</code>, exact <code>anchor_heading</code>, one-based <code>anchor_occurrence</code>, integer <code>order</code>, <code>kind</code>, <code>destination_module_id</code>, <code>title</code>, <code>summary</code>, <code>estimated_minutes</code>, and <code>prerequisites</code>. Build validation MUST fail on a missing or ambiguous anchor. Cards MUST be labelled <code>Required practice</code>, <code>Elective</code>, or <code>Optional refresher</code> and link to <code>#/learn/:destination_module_id</code>; they MUST NOT be inserted as canonical Markdown.

## UX-003 — Lesson reader and progressive disclosure

Foundation modules 00–12 MUST render their canonical bodies and heading order unchanged, followed by edition overlay cards and existing separate check/stopping controls. New modules P00, 13–20, E01, and E02 MUST render exactly seven authored sections in CUR-003 order: Outcome and boundary; Predict before running; Guided worked example; Partially scaffolded practice; Independent evidence task; Feedback and limits; Stopping point. Prediction is saved before the worked example or feedback is revealed. Progress controls and previous/next navigation follow the seven sections and are not counted as sections. The content column MUST be at most 76 characters wide. A <code>This sitting</code> rail MUST derive links from headings actually present, display duration as curriculum metadata rather than a promise, and link to related Lab, Playground, Notebook, and Evidence items.

Opening a module records the last-visited route and sets only <code>reading=true</code>. The voluntary <code>Mark read</code> action sets only <code>read=true</code> after all required sections are available; scrolling or opening disclosures does not set read. <code>practiced=true</code> is set only after submission of the independent required exercise. <code>self_checked=true</code> is set only after submission of the module check and display of its feedback; correctness, attempts, and last answer are retained separately. None of the four flags implies another. Reviewing any module MUST remain possible. Progress controls MUST describe their effect before activation and MUST NOT award <code>artifact_verified</code> or <code>assessor_reviewed</code>.

Required definitions, limitations, commands, and safety boundaries MUST remain visible in the first layer. <code>Advanced detail</code> disclosures MUST hold only derivations, raw configurations, tensor traces, and variant configurations, and MUST NOT hold a required definition, limitation, command, or safety boundary; a module that has none of these shows no such disclosure. Disclosures MUST use native <code>details/summary</code>, retain open state per module, and never hide the only route to an exercise. Novice defaults MUST select the bounded curriculum preset and list each changed value on the review screen as `{field label}: {preset value} → {new value}` followed by the field's one-sentence effect from the operation's setup copy. <code>Advanced settings</code> MUST require an explicit expand action, display a <code>Reset to lesson preset</code> action, and show every deviation in the final review.

Command blocks MUST show profile, working directory, copy button, and <code>Copying does not execute this command</code>. Static mode displays commands and import actions only. Connected mode labels companion submissions <code>Runs on this computer through the local companion</code> and requires a review screen before submission.

## UX-004 — Truthful provenance and runtime connection

Every interactive or measured surface MUST display one of these textual provenance labels at its heading:

| Provenance | Exact label | Required explanatory copy |
|---|---|---|
| exact tokenizer/browser computation | <code>Tokenizer calculation · exact browser result</code> | <code>Exact for the selected bundled tokenizer; no model weights are trained or evaluated.</code> |
| structural teaching model | <code>Structural simulation · no model execution</code> | <code>This illustrates shapes or information flow; it does not compute model predictions or attention weights.</code> |
| supplied or imported artifact | <code>Recorded result · supplied snapshot</code> or <code>Recorded result · imported snapshot</code> | <code>This record does not prove that a process is running now.</code> |
| companion job | <code>Local companion job</code> | operation, current job state, runtime version, device/profile, job ID, and last verified timestamp; queued/starting are not described as executed |

The heading label is derived from persisted `origin`, never from the route. Surfaces that show no computation, measurement or model output (lesson text, notes, forms, navigation) carry no provenance label.

| Surface | Persisted origin | Heading label | Required metadata |
|---|---|---|---|
| tokenizer tool computed in the browser | none | <code>Tokenizer calculation · exact browser result</code> | tokenizer ID and SHA-256 |
| shape, attention or prediction simulation | none | <code>Structural simulation · no model execution</code> | the explanatory copy only |
| job, or a run, checkpoint, dataset, conversation or artifact created by a job | locally_created | <code>Local companion job</code> | the companion-job metadata above; a terminal job shows its terminal state |
| run, checkpoint, dataset, conversation or artifact | shipped_fixture | <code>Recorded result · supplied snapshot</code> | object ID and SHA-256 |
| run, checkpoint, dataset, conversation or artifact | imported | <code>Recorded result · imported snapshot</code> | object ID, SHA-256, and the import_bundle job ID with its finished_at |
| v1 record migrated by progress import, or a static-mode legacy-run-v1 record, which has no origin field | legacy_imported, or none | <code>Recorded result · imported snapshot</code> | object ID and the v1 import time |

When a locally created job reads a subject, checkpoint, adapter or dataset whose origin is not locally_created, the heading keeps <code>Local companion job</code>. A second line lists each such input in request order as <code>Uses imported checkpoint ID</code>, <code>Uses imported dataset ID</code> or <code>Uses supplied fixture ID</code>. A queued, starting or cancelling job states that no execution result exists yet.

The interface MUST use the operation names in D06. Tokenizer training copy MUST say <code>Learns token merge rules; creates no neural model weights</code>. Fresh TinyLM training MUST say <code>Starts neural weights from the recorded initialization seed</code>. Resume MUST say <code>Loads model, optimizer, and random state from checkpoint and performs additional updates</code>. Evaluation and generation MUST say <code>Reads weights; performs no optimizer updates</code>. Adapter training MUST say <code>Updates adapter weights while the selected base model remains frozen</code>.

In hosted/static mode the runtime strip says <code>Static course · browser calculations, structural simulations, and recorded imports only</code>; job submission controls are disabled and adjacent to <code>Set up the local companion</code>. The setup route MUST state that the hosted page cannot run Python and direct the learner to launch the companion at <code>http://127.0.0.1:8765</code>. In companion mode, connection is established only by a successful same-origin versioned status response. The UI MUST show profile, device, runtime version, storage display path, and writable status from that response; it MUST NOT infer connection from URL, cached data, or a timer. The runtime settings page and the Lab connection panel MUST show the device line `Running on {gpu.name} (GPU) · profile {profile}` when device is cuda, or `Running on the CPU · profile {profile}` when device is cpu. Below it they show RuntimeInfo.gpu_offer as follows. For `available` with the CUDA environment installed: `A supported NVIDIA GPU is available: {gpu.name}. To use it, stop this companion and start it from the {cuda_profile} environment.` followed by a command block for `envs/{cuda_profile}/bin/python -m llm_foundations_companion serve --storage {storage_root_display}` in WSL or `envs\{cuda_profile}\Scripts\python.exe -m llm_foundations_companion serve --storage {storage_root_display}` on native Windows, with working directory `the install directory`. For `available` without it: `A supported NVIDIA GPU is available: {gpu.name}. Install the {cuda_profile} environment to use it (setup guide, GPU section).` For `unsupported`: `An NVIDIA GPU was found ({gpu.name}) but cannot be used: ` followed by the reason sentence, which is `its driver is {gpu.driver_version} and 572.61 or newer is required.` for CUDA_DRIVER_TOO_OLD, `its compute capability is {gpu.compute_capability} and 7.5 or newer (GeForce RTX 20-series or later) is required.` for CUDA_CAPABILITY_UNSUPPORTED, and `it has {gpu.memory_total_mib} MiB of memory and 3,584 MiB is required.` for CUDA_MEMORY_INSUFFICIENT. There is no offer for `in_use` or `not_detected`. On a CUDA instance the runtime settings page also shows the command block that starts the OS CPU profile, so both choices stay visible. The offer is text: it never starts, stops or switches a companion.

Connection states are <code>static</code>, <code>checking</code>, <code>connected</code>, <code>incompatible</code>, and <code>lost</code>. <code>checking</code> keeps read-only content available and disables submissions. <code>incompatible</code> shows expected and received API versions and a launch/update instruction. <code>lost</code> keeps the last verified snapshot visibly timestamped, changes any nonterminal job to <code>State unknown while disconnected</code>, offers <code>Recheck connection</code>, and never changes the job to failed or completed. Reconnection MUST fetch the job by ID, replace the snapshot only after validation, announce the reconciled state, and identify events received since the last sequence number.

Connection states are closed: <code>static</code> (hosted origin); <code>checking</code> (a request in flight); <code>needs_pairing</code> (GET /healthz succeeds, no session in this tab's sessionStorage); <code>connected</code> (GET /runtime succeeds with a compatible api_version and storage_writable true); <code>connected_read_only</code> (storage_writable false: mutations disabled with <code>Storage is in read-only recovery</code> and a link to Settings › Storage); <code>incompatible</code> (api_version differs); <code>session_expired</code> (any 401 SESSION_EXPIRED or AUTH_REQUIRED on a paired tab); <code>lost</code> (network failure). needs_pairing and session_expired show <code>Run python -m llm_foundations_companion connect --storage ROOT in your terminal and open the printed link in this tab.</code> Pairing is per tab: each tab exchanges its own bootstrap secret, and a new connect link replaces any unused one. Unsent form input is kept in sessionStorage under <code>llm-foundations-draft-v1:&lt;instance_id&gt;:&lt;route&gt;</code>, survives reload and re-pairing, is cleared on successful submit or explicit Discard and on Disconnect, and never enters exports, logs or progress. After a 401 the UI keeps every draft, blocks nothing but submission, and resubmits nothing automatically; the learner re-sends after reconciling (INT-008).

## UX-005 — Data and job setup

The Data clinic MUST use four client steps without implying a server preview endpoint. <code>1 Source</code> selects UTF-8 JSONL and captures display name, provenance statement, rights/permission statement, intended task, and sensitive-data declaration. Before selection it states <code>UTF-8 JSONL only · 1–3 files · 10 MiB per file · 30 MiB combined · 100,000 records maximum</code>, plus the 200,000 parsed UTF-8-byte TinyLM/tokenizer limit and 20 MiB parsed SFT-content limit for the selected operation. <code>2 Inspect</code> performs strict browser JSONL parsing, shows every physical-line error, record/UTF-8-byte/empty count, and five-record deterministic preview with whitespace preserved. It shows exact built-in byte-token counts only, labelled <code>Byte tokenizer calculation · exact browser result</code>; it says <code>Token count unavailable until that tokenizer/model is selected</code> for BPE/pretrained counts it cannot compute. <code>3 Split and preliminary audit</code> requires one explicit train/validation/test mapping per <code>scenario_group_id</code>; all records in a group inherit it, the mapping is persisted and no random assignment occurs. Browser audit compares unordered exact byte pairs; normalized-near pairs use the DAT-003 compared content and near normalization, including code-token and digit-run removal; group overlap counts each group present in multiple splits. Findings are labelled <code>Preliminary browser audit · server registration is authoritative</code>. <code>4 Register</code> posts the already split train/validation/test JSONL files, provenance, mapping, and preliminary audit to <code>POST /datasets</code>. Parse/schema errors block registration. A clean preliminary audit offers <code>Register dataset</code>; detected cross-split exact/near/group leakage offers <code>Save audit-only dataset</code>, states that compute operations will reject it, and permits the module's leaky-trap evidence. The authoritative server audit determines <code>eligible</code> or <code>audit_only</code>; success navigates to <code>#/lab/data/:datasetId</code> with immutable ID, digest, final findings, and eligibility.

Each <code>#/lab/new/:operation</code> form MUST be generated from runtime capabilities and the selected lesson preset. The review screen MUST list operation; starting model/tokenizer/checkpoint; dataset split IDs; settings; random seeds; requested update/token limit; device/profile; output identity allocated by the companion; files expected on success; weight-changing fields; and unchanged fields. A single <code>Submit local job</code> action creates the job. Double activation MUST create one job and return the same idempotent result. Queue full, invalid input, missing artifact, incompatible checkpoint, limit, storage, and offline responses MUST retain entries and focus the first actionable message. Field errors use `field_path` as an RFC 6901 JSON Pointer into the request body (multipart uploads: <code>/&lt;part&gt;/&lt;line&gt;/&lt;field&gt;</code>); each form keeps a pointer-to-control map, the error summary lists errors in DOM order with unmapped paths last, and focus moves to the summary. Error scope is fixed: VALIDATION_FAILED and INVALID_REQUEST are field-level when every error maps to a control and page-level otherwise; IDEMPOTENCY_CONFLICT, STATE_CONFLICT, REGISTRY_LIMIT, QUEUE_FULL, DISK_FULL, STORAGE_UNAVAILABLE, DEVICE_UNAVAILABLE, BACKEND_UNAVAILABLE and CAPABILITY_UNAVAILABLE are page-level banners with the learner message for their reason code from the error vocabulary; AUTH_REQUIRED, SESSION_EXPIRED, ORIGIN_REJECTED and CSRF_REJECTED switch to the session_expired or needs_pairing connection state. The server `message` is shown as escaped text beside the learner copy, wraps with overflow-wrap:anywhere, and never replaces the learner copy. Validation timing: character/byte counters update on input; required, enum and pattern errors appear on submit or blur of a touched field; server errors appear after the response.

## UX-006 — Job monitor, results, and checkpoints

The job monitor MUST render the runtime state without optimistic substitution:

| State | Status sentence | Enabled actions |
|---|---|---|
| <code>queued</code> | <code>Waiting for the local compute worker (position N of M).</code> | Request cancellation; leave page |
| <code>starting</code> | <code>Checking inputs and preparing the process.</code> | Request cancellation; leave page |
| <code>running</code> | <code>Running locally at step X of requested Y.</code> or operation-specific token/item count | Request cancellation; leave page |
| <code>cancelling</code> | <code>Cancellation requested; waiting for a safe checkpoint boundary.</code> | leave page |
| <code>completed</code> | <code>Completed and recorded by the local companion.</code> | Open run; open artifact; repeat as new job |
| <code>failed</code> | <code>Failed. No success is implied.</code> plus escaped learner-safe reason | Review logs; copy retry as new job |
| <code>interrupted</code> | <code>Interrupted at the last recorded boundary.</code> plus checkpoint availability | Resume from eligible checkpoint; copy retry as new job |
| disconnected nonterminal | <code>Connection lost. Job state is unknown.</code> | Recheck connection; leave page |

Cancellation wording MUST be <code>Request cancellation</code>, never Pause. Leaving the page MUST NOT cancel a job. Terminal copy is fixed by terminal_reason or error code:

| Reason/code | Headline | Allowed actions |
|---|---|---|
| user_cancelled | <code>Interrupted at your request.</code> + checkpoint availability | Resume from checkpoint (if resumable); copy retry |
| timeout | <code>Stopped at the 60-minute compute limit.</code> | Resume from checkpoint (if resumable); copy retry with the same settings (a lesson preset keeps its update count) |
| exercise_timeout | <code>Teaching hold ended after 10 minutes at saved step 25.</code> | Resume from step-25 checkpoint as a new job |
| service_restarted / service_shutdown | <code>Interrupted because the local companion stopped.</code> | Resume from checkpoint (if resumable); copy retry |
| worker_lost | <code>The worker stopped responding during cancellation.</code> | Review logs; copy retry |
| worker_ownership_unknown | <code>The companion could not prove it owns the worker; new jobs are paused.</code> | Restart the companion |
| failed + error code | <code>Failed: </code> + the code's learner message from the error vocabulary | Review logs; copy retry |

A checkpoint whose portability is not resume never offers Resume. Queued rows show <code>Waiting for the local compute worker (position N of M).</code> from Job.queue_position. Elapsed time is finished_at or now minus started_at, and every countdown (including the module-14 hold, from Job.hold_deadline_at) is computed with the offset between the browser clock and RuntimeInfo.server_time recorded at the last fetch; remaining time is visible text and is never placed in a live region. The last-visited route is kept in the per-origin UI settings key (AMD-029), not in progress. The live training chart plots only validation_nll_token points (legend <code>Validation (measured at evaluation steps)</code>) until the metrics artifact is committed, then adds the training series; the adjacent exact table has columns Step, Split, Metric, Value (six decimals) and Source (event or artifact); before the first point it shows <code>No measurements yet.</code> The downloadable event record is a JSON file of every retained event from GET /jobs/{id}/events. The monitor MUST show queued/started/updated/terminal timestamps, operation, job ID, device/profile, requested boundary, last recorded boundary, elapsed time, and ordered warnings. Elapsed time is finished_at (or now for a nonterminal job) minus started_at, and is the text `Missing` while started_at is null. Training metrics MUST provide a chart and exact table; chart axes are <code>Optimizer updates</code> and <code>Mean negative log probability (nats/token)</code>. Streaming updates MUST be throttled visually to at most four render updates per second while preserving every event in the downloadable record.
Module 14's teaching job remains <code>running</code> when runtime activity is <code>cancellable_hold</code> after saving step 25. The monitor MUST label it <code>Teaching hold · local job running</code>, say <code>Step 25 saved. The lesson is waiting for you to interrupt this run; it will not resume.</code>, show <code>Interrupt at saved step 25</code>, and show an absolute timeout time plus remaining minutes. Activating the action requests cancellation and resolves to <code>interrupted</code> at step 25. Ten minutes without action resolves to <code>interrupted</code> with reason <code>exercise_timeout</code>. The UI MUST NOT label this a pause, offer Resume for the same job, or imply additional updates can occur.


Run detail MUST separate Identity, Measurements, Samples, Checkpoint lineage, Artifacts, and <code>What this supports / does not support</code>. Comparing runs requires matching task, data split identity, tokenizer, evaluation protocol, and metric units. ## UX-007 — Playground, continuation, chat, and context disclosure

Playground MUST have two mutually exclusive modes:

1. <code>TinyLM continuation</code> accepts one text prompt and a TinyLM checkpoint. Its action is <code>Generate continuation</code>. Copy states <code>This predicts more text. It has no system, user, or assistant roles.</code>
2. <code>Pretrained chat</code> accepts a prepared base model or adapter with its required chat template. Its action is <code>Send message</code>. Copy states <code>Chatting reads the selected weights. It does not train them.</code>

Changing mode clears unsent input only after confirmation and starts a new history. A history is bound to backend, base-model revision, adapter/checkpoint digest, tokenizer/template identity, and decoding settings. Changing any bound identity requires <code>Start a new session</code>; prior outputs remain read-only. A completed chat reply is committed automatically with POST /conversations/{id}/commit-generation; until the commit succeeds the reply shows <code>Not saved to conversation</code> with one visible <code>Retry save</code>. A 409 STATE_CONFLICT shows <code>This conversation changed elsewhere. Reload it, then resend, or save this reply as a new conversation.</code> and never appends twice. <code>#/playground/history</code> lists saved conversations with subject identity, revision, turn count and updated time; opening one shows prior turns read-only until <code>Continue this conversation</code>. Deletion uses the deletion-preview token and dialog; <code>Export chat as data</code> requires the sensitive-text confirmation and creates an unregistered dataset-candidate artifact. <code>Start a new session</code> creates a new conversation. TinyLM output MUST visually distinguish prompt from generated continuation. Chat MUST distinguish system, user, assistant, and tool-free template boundaries; it MUST NOT present TinyLM as a chatbot.

Before generation, <code>Preview context</code> submits the queued <code>context_preview</code> companion operation. Its copy states <code>Tokenizes and serializes context only; no weights are loaded or updated and no inference runs.</code> On completion, a <code>Context sent to the model</code> disclosure shows exact serialized text/tokens, total token count, model limit, teaching effective limit, retained range, truncated content count, and <code>context_preview_digest</code>. If truncation occurs, an always-visible warning identifies whether oldest chat turns or leftmost continuation tokens were removed. Raw context MUST preserve spaces, tabs, and newlines. <code>Generate continuation</code> or <code>Send message</code> remains disabled until a successful preview exists. Changing subject/model/checkpoint/adapter, prompt/messages, chat template, context limit, maximum new tokens, or any serialization/truncation field immediately invalidates the digest, returns focus to <code>Preview context</code>, and requires a new preview. The generation request MUST submit the matching preview digest. Stale preview has one learner outcome whatever its source (client field change, 400 VALIDATION_FAILED reason CONTEXT_PREVIEW_STALE, or a generation job failed with CONTEXT_PREVIEW_STALE): <code>The context changed after it was previewed. Nothing was generated. Preview the context again.</code>; prompt/messages are kept, the stored digest is cleared, focus moves to <code>Preview context</code>, and nothing is resubmitted. A context_preview job that fails with CONTEXT_TOO_LONG shows <code>The conversation is too long for the 512-token context even after dropping older turns.</code> with the counts. Because preview is a queued job, a queued preview shows <code>Preview queued behind N job(s)</code> with <code>Request cancellation</code>, and the generate/send action states <code>Preview the context first</code> while disabled. Output shows model identity, checkpoint/adapter, seed, temperature, maximum new tokens, stop reason, generated token count, elapsed time (finished_at minus started_at), and job ID.

Checkpoint comparison supports two to four checkpoints of the same backend/tokenizer/config compatibility class. It submits identical prompt/context, seed, temperature, and maximum tokens as separate sequential jobs; the UI MUST show queued ordering and MUST NOT imply simultaneous execution. Outputs appear in aligned labelled columns at 1440 and stacked labelled sections at 360/768. Any setting mismatch blocks comparison until reset.

## UX-011 — Empty, loading, failure, interruption, and recovery states

Every collection or asynchronous surface MUST implement this state contract:

| State | Required rendering | Recovery |
|---|---|---|
| empty | heading names what is absent; reason; one valid next action | create/import/open supplied example |
| loading | visible text `Loading {subject}…` where {subject} is the route's plural noun; existing content remains visible and unchanged until the new content has fully arrived and is then replaced in one step; the control that started the load is disabled once | wait; `Request cancellation` only while the subject is a queued, starting or running job, otherwise no cancel control |
| offline/static | last verified data timestamped; no changing-state action enabled | setup or Recheck connection |
| malformed import | escaped filename; failed rule; no partial write | choose another file; download error report |
| conflict preview | both identities/timestamps, the proposed resolution and the allowed resolutions for each divergent item | choose a resolution for each divergent item, then apply; or cancel |
| job failed | terminal state, escaped reason, retained logs/artifacts, no success styling | copy retry as new job |
| job interrupted | last recorded boundary and eligible checkpoint or <code>No resumable checkpoint</code> | resume or copy retry |
| storage failure | unsaved indicator and session copy retained | retry save; export download |
| reconnect | checking text; stale snapshot unchanged | validated reconciliation or remain lost |

Retry MUST create a new attempt ID and retain the earlier attempt. Existing output, dataset, run, checkpoint, note, or evidence records MUST never be overwritten by a UI retry. File-picker cancellation is neutral and MUST produce no error. Destructive removal, where allowed by the data contract, requires a dialog naming the exact item and consequences; it cannot be the primary action.

## UX-012 — Required end-to-end learner journeys

The release MUST support these exact sequences:

1. Foundation continuation: new Home → module 00 → explanation → practice feedback → stopping-point note → read/practiced/self-checked distinctions → leave → return Home → Continue resolves to the next required action.
2. Local connection: static Lab → setup → launch companion externally → open companion origin → verified status/preflight → local Lab without carrying unverified hosted state.
3. Data to training: Data clinic source → inspect → split → audit → immutable dataset → TinyLM setup/review → queued/running → completed or retained failed/interrupted run.
4. Results to explanation: run → exact metric table and sample → limitations → linked notebook entry → evidence criterion without automatic human-review credit.
5. Playground reuse: select a TinyLM checkpoint by checkpoint ID (best and last labelled) → disclose/truncate context → continuation → compare eligible checkpoints sequentially → retain identity and decoding settings.
6. Applied chat: prepare pinned pretrained base → select base or adapter → inspect serialized chat context → send → output metadata → explicit export before any future dataset import.
7. Independent assessment: required criteria → artifact verifier facts → written rubric → identified self/independent review → unresolved items remain visible → export bundle.
