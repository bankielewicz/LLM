# Learner experience specification — Intermediate buildout v1

Status: NORMATIVE TARGET. Product behavior described here is not implemented or tested by this specification task. This document is subordinate to [00-DECISIONS.md](00-DECISIONS.md).

The existing interface establishes the calm workshop, single continuation action, short-session lesson rhythm, distinct progress marks, simulations, recorded-run reading, notebook, and evidence checklist that this release extends. The current route switch and screens are in [dist/app.js](../../../dist/app.js#L10-L45); current visual tokens and breakpoints are in [dist/styles.css](../../../dist/styles.css#L1-L8). The source interaction contract requires exact content rendering, honest recorded-data labels, independent progress storage, and distinguishable simulation, record, connection, checkpoint, and storage states ([course/design/INTERACTION_CONTRACT.md](../../../course/design/INTERACTION_CONTRACT.md#L5-L38)).

## UX-001 — Application shell, routes, and navigation

The application MUST expose the following canonical hash routes. Refreshing or directly opening any route MUST render that route on static basic hosting without server rewrites. Existing <code>#/lesson/:moduleId</code> links MUST use <code>history.replaceState</code> once to become <code>#/learn/:moduleId</code>, without adding a history entry, losing query state, or changing progress.

| Route | Primary heading | Required information hierarchy | Primary action |
|---|---|---|---|
| <code>#/</code> | Continue learning / Start learning | next required activity; why it matters; duration; foundation/applied progress; unresolved evidence; runtime strip | Open next activity |
| <code>#/learn</code> | Learning path | foundations 00–12; applied 13–20; optional P00; electives E01/E02; per-module state and prerequisites | Open next required module |
| <code>#/learn/:moduleId</code> | module title | outcome; explanation; worked example; practice; feedback; stopping point; linked lab/evidence | Continue to next required activity |
| <code>#/lab</code> | Local lab | connection/preflight; dataset; operation; bounded preset; exact effects; queue summary | Continue setup or review submission |
| <code>#/lab/data</code> | Data clinic | selected source; provenance; split; audit findings; immutable dataset identity | Create audited dataset |
| <code>#/lab/data/:datasetId</code> | dataset display name | immutable identity/digest; provenance; split counts; audit findings; linked runs/artifacts | Use in an eligible operation |
| <code>#/lab/new/:operation</code> | operation-specific setup | starting artifact; fields changed; fields frozen; limits; estimate stated as unknown unless measured; review | Submit local job |
| <code>#/lab/jobs/:jobId</code> | job name | truthful state; operation; progress/metrics; messages; artifacts; recovery actions | state-dependent action in UX-006 |
| <code>#/runs</code> | Runs | filter; comparable run groups; operation/status/backend; retained failures | Open selected run |
| <code>#/runs/:runId</code> | run name | identity; status; metrics; samples; lineage; protocol; artifacts; interpretation limits | Open next valid action |
| <code>#/playground</code> | Playground | mode; selected model/checkpoint; context disclosure; input; decoding; output; history | Generate continuation or Send message |
| <code>#/notebook</code> | Experiment notebook | entries; linked artifacts; prediction/observation/explanation/limitations/next experiment; export/import | Create entry |
| <code>#/evidence</code> | Intermediate evidence | foundation evidence; required modules 13–20; objective verification; written rubric; review identity; unresolved items | Open next unresolved item |
| <code>#/search</code> | Search course | bounded query; result count; title/outcome/heading/glossary matches; empty/no-match state | Open selected result |
| <code>#/settings/runtime</code> | Local runtime | supported launch instructions or verified companion status; profile/device/version/capabilities | Copy launch command or Recheck connection |
| <code>#/settings/storage</code> | Storage and backups | active scope; location; usage; export/import/migration | Export backup |
| <code>#/settings/accessibility</code> | Reading and access | theme; text density; motion preference; table/chart alternatives | Save preferences |

The persistent primary navigation MUST contain Home, Learn, Lab, Runs, Playground, Notebook, and Evidence in that order. Settings MUST be reachable from the application header. The current page MUST use <code>aria-current="page"</code>; a module link MUST announce its module ID, title, required/elective kind, and progress state. Every nested page MUST provide one contextual back link that returns to its parent without discarding form state. Browser Back and Forward MUST restore the route, scroll position, selected tab, and unsent form fields held in session memory.

The global header MUST contain the current section name, runtime status button, storage status text, Search, and Settings. Runtime status labels are exactly <code>Static course</code>, <code>Checking local runtime</code>, <code>Local runtime connected</code>, or <code>Connection lost</code>. No green dot or icon may be the only status indication.

Search accepts 1–100 Unicode scalar values, applies Unicode NFKC, casefolding, Unicode-whitespace collapse and trim, then literal substring matching; it performs no stemming or synonym expansion. Searchable fields are module title, outcome, authored heading, glossary term, and glossary definition. Rank is exact title/term, title/term prefix, title/outcome/heading/term substring, then definition substring; ties use curriculum order, source heading order, then glossary term code-point order. Return at most 50 results. Submitting an empty normalized query focuses <code>Search results</code> and displays <code>Enter a word or phrase to search the course.</code>; no matches focuses the same heading and displays <code>No course matches for “QUERY”.</code>. Result links identify field and module, focus the destination heading, and MUST NOT mutate progress.

## UX-002 — Home, learning path, and continuation

Home MUST present exactly one visually primary action. For a new learner it is <code>Start learning</code> and targets module 00 unless the learner explicitly chooses P00. For a returning learner it is <code>Continue learning</code>. Progress dimensions are independent booleans/timestamps, never an ordered enum. Its deterministic target order is: the most recently updated required module with <code>reading=true</code> and <code>read=false</code>; the most recently updated required module with <code>read=true</code> and either <code>practiced=false</code> or <code>self_checked=false</code>; the lowest-sequence unresolved required evidence item whose prerequisites are met; the lowest-sequence required module with at least one true and at least one false learning flag; then the lowest-sequence required module whose four flags are false. Timestamp ties use curriculum sequence ascending. When all four learning flags are true for all required modules, Continue targets <code>#/evidence</code>: the next unresolved required criterion when one exists, otherwise the evidence summary with primary action <code>Review evidence and export</code>. A failed or interrupted job MUST appear immediately below the primary action as <code>Review interrupted job</code> or <code>Review failed job</code>; it MUST NOT replace course continuation or imply failure completion.

Home MUST show separate counts for Read, Practiced, Self-checked, Artifact verified, and Independently reviewed. It MUST NOT collapse these into a completion percentage. The learning path MUST show P00 outside the required sequence, foundations 00–12 as preserved content, required applied modules 13–20, and electives E01/E02 in distinct labelled groups. Locked prerequisites MUST explain the exact prerequisite and provide a link to it; navigation remains available for review, and only the dependent graded practice submission is disabled.

The foundation bodies MUST remain unchanged. Supplement cards are an edition overlay with <code>card_id</code>, <code>source_lesson_id</code>, exact <code>anchor_heading</code>, one-based <code>anchor_occurrence</code>, integer <code>order</code>, <code>kind</code>, <code>destination_module_id</code>, <code>title</code>, <code>summary</code>, <code>estimated_minutes</code>, and <code>prerequisites</code>. Build validation MUST fail on a missing or ambiguous anchor. Cards MUST be labelled <code>Required practice</code>, <code>Elective</code>, or <code>Optional refresher</code> and link to <code>#/learn/:destination_module_id</code>; they MUST NOT be inserted as canonical Markdown.

## UX-003 — Lesson reader and progressive disclosure

Foundation modules 00–12 MUST render their canonical bodies and heading order unchanged, followed by edition overlay cards and existing separate check/stopping controls. New modules P00, 13–20, E01, and E02 MUST render exactly seven authored sections in CUR-003 order: Outcome and boundary; Predict before running; Guided worked example; Partially scaffolded practice; Independent evidence task; Feedback and limits; Stopping point. Prediction is saved before the worked example or feedback is revealed. Progress controls and previous/next navigation follow the seven sections and are not counted as sections. The content column MUST be at most 76 characters wide. A <code>This sitting</code> rail MUST derive links from headings actually present, display duration as curriculum metadata rather than a promise, and link to related Lab, Playground, Notebook, and Evidence items.

Opening a module records the last-visited route and sets only <code>reading=true</code>. The voluntary <code>Mark read</code> action sets only <code>read=true</code> after all required sections are available; scrolling or opening disclosures does not set read. <code>practiced=true</code> is set only after submission of the independent required exercise. <code>self_checked=true</code> is set only after submission of the module check and display of its feedback; correctness, attempts, and last answer are retained separately. None of the four flags implies another. Reviewing any module MUST remain possible. Progress controls MUST describe their effect before activation and MUST NOT award <code>artifact_verified</code> or <code>assessor_reviewed</code>.

Required definitions, limitations, commands, and safety boundaries MUST remain visible in the first layer. <code>Advanced detail</code> disclosures MAY contain derivations, raw configurations, tensor traces, and optional variants. Disclosures MUST use native <code>details/summary</code>, retain open state per module, and never hide the only route to an exercise. Novice defaults MUST select the bounded curriculum preset and explain each changed value in plain language. <code>Advanced settings</code> MUST require an explicit expand action, display a <code>Reset to lesson preset</code> action, and show every deviation in the final review.

Command blocks MUST show profile, working directory, copy button, and <code>Copying does not execute this command</code>. Static mode displays commands and import actions only. Connected mode labels companion submissions <code>Runs on this computer through the local companion</code> and requires a review screen before submission.

## UX-004 — Truthful provenance and runtime connection

Every interactive or measured surface MUST display one of these textual provenance labels at its heading:

| Provenance | Exact label | Required explanatory copy |
|---|---|---|
| exact tokenizer/browser computation | <code>Tokenizer calculation · exact browser result</code> | <code>Exact for the selected bundled tokenizer; no model weights are trained or evaluated.</code> |
| structural teaching model | <code>Structural simulation · no model execution</code> | <code>This illustrates shapes or information flow; it does not compute model predictions or attention weights.</code> |
| supplied or imported artifact | <code>Recorded result · supplied snapshot</code> or <code>Recorded result · imported snapshot</code> | <code>This record does not prove that a process is running now.</code> |
| companion job | <code>Local companion job</code> | operation, current job state, runtime version, device/profile, job ID, and last verified timestamp; queued/starting are not described as executed |

The interface MUST use the operation names in D06. Tokenizer training copy MUST say <code>Learns token merge rules; creates no neural model weights</code>. Fresh TinyLM training MUST say <code>Starts neural weights from the recorded initialization seed</code>. Resume MUST say <code>Loads model, optimizer, and random state from checkpoint and performs additional updates</code>. Evaluation and generation MUST say <code>Reads weights; performs no optimizer updates</code>. Adapter training MUST say <code>Updates adapter weights while the selected base model remains frozen</code>.

In hosted/static mode the runtime strip says <code>Static course · browser calculations, structural simulations, and recorded imports only</code>; job submission controls are disabled and adjacent to <code>Set up the local companion</code>. The setup route MUST state that the hosted page cannot run Python and direct the learner to launch the companion at <code>http://127.0.0.1:8765</code>. In companion mode, connection is established only by a successful same-origin versioned status response. The UI MUST show profile, device, runtime version, storage display path, and writable status from that response; it MUST NOT infer connection from URL, cached data, or a timer.

Connection states are <code>static</code>, <code>checking</code>, <code>connected</code>, <code>incompatible</code>, and <code>lost</code>. <code>checking</code> keeps read-only content available and disables submissions. <code>incompatible</code> shows expected and received API versions and a launch/update instruction. <code>lost</code> keeps the last verified snapshot visibly timestamped, changes any nonterminal job to <code>State unknown while disconnected</code>, offers <code>Recheck connection</code>, and never changes the job to failed or completed. Reconnection MUST fetch the job by ID, replace the snapshot only after validation, announce the reconciled state, and identify events received since the last sequence number.

## UX-005 — Data and job setup

The Data clinic MUST use four client steps without implying a server preview endpoint. <code>1 Source</code> selects UTF-8 JSONL and captures display name, provenance statement, rights/permission statement, intended task, and sensitive-data declaration. Before selection it states <code>UTF-8 JSONL only · 1–3 files · 10 MiB per file · 30 MiB combined · 100,000 records maximum</code>, plus the 200,000 parsed UTF-8-byte TinyLM/tokenizer limit and 20 MiB parsed SFT-content limit for the selected operation. <code>2 Inspect</code> performs strict browser JSONL parsing, shows every physical-line error, record/UTF-8-byte/empty count, and five-record deterministic preview with whitespace preserved. It shows exact built-in byte-token counts only, labelled <code>Byte tokenizer calculation · exact browser result</code>; it says <code>Token count unavailable until that tokenizer/model is selected</code> for BPE/pretrained counts it cannot compute. <code>3 Split and preliminary audit</code> requires one explicit train/validation/test mapping per <code>scenario_group_id</code>; all records in a group inherit it, the mapping is persisted and no random assignment occurs. Browser audit compares unordered exact byte pairs; normalized-near pairs use NFKC, casefold, punctuation/symbol-to-ASCII-space, Unicode-whitespace collapse and trim; group overlap counts each group present in multiple splits. Findings are labelled <code>Preliminary browser audit · server registration is authoritative</code>. <code>4 Register</code> posts the already split train/validation/test JSONL files, provenance, mapping, and preliminary audit to <code>POST /datasets</code>. Parse/schema errors block registration. A clean preliminary audit offers <code>Register dataset</code>; detected cross-split exact/near/group leakage offers <code>Save audit-only dataset</code>, states that compute operations will reject it, and permits the module's leaky-trap evidence. The authoritative server audit determines <code>eligible</code> or <code>audit_only</code>; success navigates to <code>#/lab/data/:datasetId</code> with immutable ID, digest, final findings, and eligibility.

Each <code>#/lab/new/:operation</code> form MUST be generated from runtime capabilities and the selected lesson preset. The review screen MUST list operation; starting model/tokenizer/checkpoint; dataset split IDs; settings; random seeds; requested update/token limit; device/profile; output identity allocated by the companion; files expected on success; weight-changing fields; and unchanged fields. A single <code>Submit local job</code> action creates the job. Double activation MUST create one job and return the same idempotent result. Queue full, invalid input, missing artifact, incompatible checkpoint, limit, storage, and offline responses MUST retain entries and focus the first actionable message.

## UX-006 — Job monitor, results, and checkpoints

The job monitor MUST render the runtime state without optimistic substitution:

| State | Status sentence | Enabled actions |
|---|---|---|
| <code>queued</code> | <code>Waiting for the local compute worker.</code> | Cancel job; leave page |
| <code>starting</code> | <code>Checking inputs and preparing the process.</code> | Cancel job; leave page |
| <code>running</code> | <code>Running locally at step X of requested Y.</code> or operation-specific token/item count | Request cancellation; leave page |
| <code>cancelling</code> | <code>Cancellation requested; waiting for a safe checkpoint boundary.</code> | leave page |
| <code>completed</code> | <code>Completed and recorded by the local companion.</code> | Open run; open artifact; repeat as new job |
| <code>failed</code> | <code>Failed. No success is implied.</code> plus escaped learner-safe reason | Review logs; copy retry as new job |
| <code>interrupted</code> | <code>Interrupted at the last recorded boundary.</code> plus checkpoint availability | Resume from eligible checkpoint; copy retry as new job |
| disconnected nonterminal | <code>Connection lost. Job state is unknown.</code> | Recheck connection; leave page |

Cancellation wording MUST be <code>Request cancellation</code>, never Pause. Leaving the page MUST NOT cancel a job. The monitor MUST show queued/started/updated/terminal timestamps, operation, job ID, device/profile, requested boundary, last recorded boundary, elapsed time when reported, and ordered warnings. Training metrics MUST provide a chart and exact table; chart axes are <code>Optimizer updates</code> and <code>Mean negative log probability (nats/token)</code>. Streaming updates MUST be throttled visually to at most four render updates per second while preserving every event in the downloadable record.
Module 14's teaching job remains <code>running</code> when runtime activity is <code>cancellable_hold</code> after saving step 25. The monitor MUST label it <code>Teaching hold · local job running</code>, say <code>Step 25 saved. The lesson is waiting for you to interrupt this run; it will not resume.</code>, show <code>Interrupt at saved step 25</code>, and show an absolute timeout time plus remaining minutes. Activating the action requests cancellation and resolves to <code>interrupted</code> at step 25. Ten minutes without action resolves to <code>interrupted</code> with reason <code>exercise_timeout</code>. The UI MUST NOT label this a pause, offer Resume for the same job, or imply additional updates can occur.


Run detail MUST separate Identity, Measurements, Samples, Checkpoint lineage, Artifacts, and <code>What this supports / does not support</code>. Comparing runs requires matching task, data split identity, tokenizer, evaluation protocol, and metric units. When any field differs, the UI MUST list differences above the chart and disable an aggregate delta statement. Best-observed and latest-saved checkpoints MUST be separate rows with step, validation selection rule, digest, and availability. Missing means <code>Missing</code>, never step zero. A failed/interrupted run remains in Runs and is visually equal in density to a completed run.

## UX-007 — Playground, continuation, chat, and context disclosure

Playground MUST have two mutually exclusive modes:

1. <code>TinyLM continuation</code> accepts one text prompt and a TinyLM checkpoint. Its action is <code>Generate continuation</code>. Copy states <code>This predicts more text. It has no system, user, or assistant roles.</code>
2. <code>Pretrained chat</code> accepts a prepared base model or adapter with its required chat template. Its action is <code>Send message</code>. Copy states <code>Chatting reads the selected weights. It does not train them.</code>

Changing mode clears unsent input only after confirmation and starts a new history. A history is bound to backend, base-model revision, adapter/checkpoint digest, tokenizer/template identity, and decoding settings. Changing any bound identity requires <code>Start a new session</code>; prior outputs remain read-only. TinyLM output MUST visually distinguish prompt from generated continuation. Chat MUST distinguish system, user, assistant, and tool-free template boundaries; it MUST NOT present TinyLM as a chatbot.

Before generation, <code>Preview context</code> submits the queued <code>context_preview</code> companion operation. Its copy states <code>Tokenizes and serializes context only; no weights are loaded or updated and no inference runs.</code> On completion, a <code>Context sent to the model</code> disclosure shows exact serialized text/tokens, total token count, model limit, teaching effective limit, retained range, truncated content count, and <code>context_preview_digest</code>. If truncation occurs, an always-visible warning identifies whether oldest chat turns or leftmost continuation tokens were removed. Raw context MUST preserve spaces, tabs, and newlines. <code>Generate continuation</code> or <code>Send message</code> remains disabled until a successful preview exists. Changing subject/model/checkpoint/adapter, prompt/messages, chat template, context limit, maximum new tokens, or any serialization/truncation field immediately invalidates the digest, returns focus to <code>Preview context</code>, and requires a new preview. The generation request MUST submit the matching preview digest. Output shows model identity, checkpoint/adapter, seed, temperature, maximum new tokens, stop reason, generated token count, elapsed time when reported, and job ID.

Checkpoint comparison supports two to four checkpoints of the same backend/tokenizer/config compatibility class. It submits identical prompt/context, seed, temperature, and maximum tokens as separate sequential jobs; the UI MUST show queued ordering and MUST NOT imply simultaneous execution. Outputs appear in aligned labelled columns at 1440 and stacked labelled sections at 360/768. Any setting mismatch blocks comparison until reset.

## UX-008 — Notebook, evidence, storage migration, and imports

In companion mode, notebook entries MUST implement <code>notebook-entry-v2</code>: stable UUID, revision, timestamps, up to eight links of each type—module, dataset, run, and checkpoint—and sixteen artifact links, plus Prediction, Observation, Explanation, Limitations, and Next experiment fields, each limited to 20,000 Unicode scalar values; at most 1,000 live notes exist. Autosave MUST expose <code>Saving</code>, <code>Saved locally at HH:MM</code>, or <code>Save failed · export recommended</code>; it MUST retain unsaved session text after a failed save. Artifacts display name, type, size, SHA-256, created time, and preview policy. An explicit Preview text action for a <code>text</code>-policy artifact with <code>size_bytes &lt;= 262144</code> MUST show escaped text; larger safe text is downloadable and labelled <code>Preview unavailable above 256 KiB</code>. Metadata-only and download-only artifacts MUST not be inlined.

Evidence MUST display required foundation and module 13–20 criteria separately from elective badges. A local submission uses <code>claim_status:local_submission</code>; an imported assertion uses <code>claim_status:imported_claim</code>. Objective checks change <code>verification_status</code> only from <code>unverified</code> to <code>artifact_verified</code> and show verifier version, checked artifact IDs/digests, timestamp, and pass/fail facts. Written rubric controls choose <code>review_kind:self</code> or <code>review_kind:independent</code> and decision <code>meets</code>, <code>partially_meets</code>, or <code>does_not_meet</code>; independent review requires a human reviewer display name, and both preserve comments. Derived <code>review_status</code> renders exactly <code>Not reviewed</code>, <code>Self-reviewed</code>, or <code>Independently reviewed</code>. An imported assertion remains <code>Imported claim · not reviewed</code> until a new local assessment. The page MUST say <code>Verification checks artifacts and objective criteria. It does not grade your explanation or certify competence.</code> An elective cannot satisfy a required criterion.

Static mode MUST retain <code>llm-foundations-progress-v1</code> unchanged and store intermediate state separately at <code>llm-foundations-intermediate-v1</code>. Before every sidecar write, it computes <code>JSON.stringify(value).length * 2</code>; more than 4,194,304 bytes or more than 100 live notes rejects the write without replacing the prior value and shows <code>Static storage limit reached · export or remove notes.</code> The sidecar may contain progress, notes, conversations, self reviews, and imported evidence claims. Static MUST NOT create <code>artifact_verified</code> or <code>independently_reviewed</code>; those controls say <code>Requires the local companion</code>.

Portable learning-state export uses format <code>llm-foundations-learning-state-v1</code>, edition <code>intermediate-v1</code>, progress plus selected notes/evidence claims/conversations, a payload digest, and no credentials. Exact UTF-8 output over 8,388,608 bytes fails with visible code <code>BACKUP_TOO_LARGE</code>, produces no partial download, and in companion mode offers <code>Export full .lfbundle</code>. A companion <code>.lfbundle</code> uses <code>llm-foundations-bundle-v1</code> for selected rich state and artifacts. Import states are <code>empty</code>, <code>reading</code>, <code>validating</code>, <code>preview</code>, <code>applying</code>, <code>applied</code>, and <code>rejected</code>. Preview MUST show source surface/installation/app version, counts for imported/skipped/conflict items, and changes by progress, notes, conversations, evidence claims, settings, and records. An identical duplicate is labelled <code>Skip duplicate</code>; a valid divergent item is labelled <code>Import as copy · fresh local IDs allocated on apply</code>. Only a successful companion apply result shows the complete source-to-local ID map. Import MUST NOT set artifact verification or independent review from claims. Applying requires <code>Import reviewed items</code>; Cancel leaves storage byte-for-byte unchanged.

Foundation migration MUST be explicit. Static and companion storage pages offer <code>Preview foundation progress migration</code> only after the learner selects an exported v1 backup; neither probes another origin or silently reads the retained v1 key. Preview retains exact selected bytes, maps each v1 <code>reading</code>, <code>read</code>, and <code>practiced</code> flag only to its same-named v2 flag, maps v1 <code>checked</code> only to v2 <code>self_checked</code>, maps notes, and displays every unmapped field. No progress flag promotes another. Collision behavior follows [DAT-008](05-DATA-AND-ARTIFACTS.md#dat-008--merge-collisions-and-duplicate-imports) and MUST be rendered item by item. Apply is atomic. Failure preserves v1 and v2; success reports the committed digest and keeps the v1 backup. No route visit, filename match, or imported run may manufacture progress or evidence.

## UX-009 — Visual system and responsive layouts

The visual system MUST retain the technical-workshop character and use semantic tokens rather than literal component colors. Light tokens are <code>background #f6f8fb</code>, <code>surface #ffffff</code>, <code>navigation #edf1f6</code>, <code>text #24334a</code>, <code>muted #59687b</code>, <code>border #d7dfe9</code>, <code>action #315bae</code>, <code>focus #986400</code>, <code>recorded #14675e</code>, <code>simulation #805218</code>, <code>error #8a3b12</code>. Dark tokens are <code>background #131d2b</code>, <code>surface #1b283b</code>, <code>navigation #172234</code>, <code>text #e5ecf6</code>, <code>muted #afbdd0</code>, <code>border #3c4d65</code>, <code>action #a7c5ff</code>, <code>focus #edc366</code>, <code>recorded #95dec7</code>, <code>simulation #f0cc8b</code>, <code>error #ffc49b</code>. Text, token IDs, vectors, model weights, targets, measurements, warnings, and errors MUST pair color with a visible label, shape, line pattern, or icon plus accessible name.

Text, muted, action, recorded, simulation, and error foregrounds MUST appear only on background or surface tokens. A light primary action uses <code>#ffffff</code> text on action; a dark primary action uses <code>#131d2b</code> text on action. Interactive control boundaries MUST use the theme's muted token; the border token is limited to decorative separators or redundant panel edges and MUST NOT be the sole visible control, focus, selected, status, chart, or information boundary. Focus uses a three-pixel focus-token outline plus four-pixel offset and is never replaced by the border token.

Body type is <code>Segoe UI, system-ui, sans-serif</code>; display headings are <code>Georgia, serif</code>; code is <code>Consolas, SFMono-Regular, monospace</code>. Sizes are 14, 16, 18, 22, 32, and 40px; 40px is used only for a page title at 1440. Spacing uses 4, 8, 12, 16, 24, 32, 48, and 64px. Controls have at least 44 by 44 CSS pixels. Panels use 12px radius and one-pixel borders; status is not conveyed by shadow.

Accessibility settings use closed values: Theme <code>system</code> (default), <code>light</code>, <code>dark</code>; Reading density <code>comfortable</code> (default: body 16px/1.65, paragraph gap 18px, panel padding 28px) or <code>compact</code> (body 15px/1.55, paragraph gap 12px, panel padding 20px); Motion <code>system</code> (default) or <code>reduce</code>; Results presentation <code>visual_and_table</code> (default) or <code>table_first</code>. Reduce disables the same behaviors as reduced-motion media preference. Table-first places the exact table before the chart without hiding either. Settings persist independently of learning progress, and Reset restores these four defaults.

At 360px, the shell is one column with a 64px sticky header, menu-button drawer no wider than 320px, 16px page gutters, stacked cards/forms/metrics, full-width primary action, and labelled stacked comparison outputs. Tables and code blocks may scroll inside their labelled region; the page itself MUST have no horizontal scroll. At 768px, navigation remains a drawer, gutters are 24px, forms use one column, and paired read-only result panels may use two equal columns only when each remains at least 320px. At 1440px, a 256px persistent navigation rail and content area are shown; main content is at most 1120px, reader body at most 76ch with a 220px sticky sitting rail, and setup screens use a 2:1 form/summary grid. Above and below these points CSS flows continuously; no content or action disappears because of width.

## UX-010 — Keyboard, focus, announcements, and display adaptations

All routes MUST begin with a <code>Skip to main content</code> link. Landmark order is header, primary navigation, main, then footer. DOM and visual order MUST match. Every action is reachable and operable with Tab, Shift+Tab, Enter, and Space as native semantics require. Custom grid/chart interaction MUST have an adjacent HTML table and MUST NOT capture arrow keys unless focus is inside a documented composite widget. Escape closes a drawer/dialog and returns focus to its opener. Opening a route focuses <code>main tabindex="-1"</code>; in-page validation focuses the error summary, whose links focus the invalid field. After modal confirmation, focus returns to the initiating control; after deletion or cancellation, it moves to the next logical heading.

Polite live announcements are limited to save completion, connection change, queued position change, no-more-than-once-per-five-seconds job progress summaries, import completion, and generation completion. Validation, job failure, incompatible runtime, and lost unsaved storage use assertive alerts once; repeated stream events MUST not repeat the alert. Visible text must remain beside live regions.

At 200% text size, content MUST reflow without clipped text or overlapping controls. At 400% browser zoom in a 1280px viewport, behavior MUST match the 360px layout and retain all information/actions without two-dimensional page scrolling. With <code>prefers-reduced-motion: reduce</code>, animation and smooth scrolling MUST be disabled; progress changes use text and static graphics. With forced colors active, borders use system colors, focus uses <code>Highlight</code>, selected states use <code>Highlight/HighlightText</code>, SVG lines use <code>currentColor</code>, and status patterns/labels remain. Light and dark themes MUST meet WCAG 2.2 AA contrast: 4.5:1 normal text, 3:1 large text and graphical/control boundaries. Theme choice MUST respect system preference until explicitly selected.

## UX-011 — Empty, loading, failure, interruption, and recovery states

Every collection or asynchronous surface MUST implement this state contract:

| State | Required rendering | Recovery |
|---|---|---|
| empty | heading names what is absent; reason; one valid next action | create/import/open supplied example |
| loading | visible subject-specific text; existing content remains when safe; control disabled once | wait or Cancel when supported |
| offline/static | last verified data timestamped; no changing-state action enabled | setup or Recheck connection |
| malformed import | escaped filename; failed rule; no partial write | choose another file; download error report |
| conflict preview | both identities/timestamps and deterministic proposed resolution | select allowed resolution or cancel |
| job failed | terminal state, escaped reason, retained logs/artifacts, no success styling | copy retry as new job |
| job interrupted | last recorded boundary and eligible checkpoint or <code>No resumable checkpoint</code> | resume or copy retry |
| storage failure | unsaved indicator and session copy retained | retry save; export download |
| reconnect | checking text; stale snapshot unchanged | validated reconciliation or remain lost |

Retry MUST create a new attempt ID and retain the earlier attempt. Existing output, dataset, run, checkpoint, note, or evidence records MUST never be overwritten by a UI retry. File-picker cancellation is neutral and MUST produce no error. Destructive removal, where allowed by the data contract, requires a dialog naming the exact item and consequences; it cannot be the primary action.

## UX-012 — Required end-to-end learner journeys

The release MUST support these exact sequences:

1. Foundation continuation: new Home → module 00 → explanation → practice feedback → stopping-point note → read/practiced/self-checked distinctions → leave → return Home → Continue resolves to the next required action.
2. Local connection: static Lab → setup → launch companion externally → open companion origin → verified status/preflight → local Lab without carrying unverified hosted state.
3. Data to training: Data clinic source → inspect → split → audit → immutable dataset → TinyLM setup/review → queued/running → completed or retained failed/interrupted run.
4. Results to explanation: run → exact metric table and sample → limitations → linked notebook entry → evidence criterion without automatic human-review credit.
5. Playground reuse: select TinyLM checkpoint → disclose/truncate context → continuation → compare eligible checkpoints sequentially → retain identity and decoding settings.
6. Applied chat: prepare pinned pretrained base → select base or adapter → inspect serialized chat context → send → output metadata → explicit export before any future dataset import.
7. Independent assessment: required criteria → artifact verifier facts → written rubric → identified self/independent review → unresolved items remain visible → export bundle.
